# 成本与性能说明

我记录成本和延迟，不只是为了给出一个费用数字，也为了验证 `batch_size=1` 是否值得保留。当前结论是：逐条抽取增加了请求往返，但换来的证据归属、精确重试和失败隔离更有价值；在这批数据和当前价格下，小批量带来的直接费用收益很小。

## 统计口径

本说明基于 `data/runs/2026-08-12/manifests/run.json` 中的真实 DeepSeek 使用量。抽取阶段来自首次在线运行；报告阶段来自升级为 `report-v3` 后的真实运行。Token 数以 Provider 返回结果为准。

费用使用 2026-08-12 查阅的 [DeepSeek `deepseek-chat` 人民币价格表](https://api-docs.deepseek.com/quick_start/pricing-details-cny/)估算：

| Token 类型 | 单价（每百万 Token） |
|---|---:|
| 输入，缓存命中 | ¥0.5 |
| 输入，缓存未命中 | ¥2 |
| 输出 | ¥8 |

DeepSeek 可能调整价格，实际账单以运行时控制台为准。本页估算不包含本地计算、电力和人工时间。

## 真实请求与 Token

| 阶段 | 请求 | 输入 Token | 缓存命中 | 缓存未命中 | 输出 Token |
|---|---:|---:|---:|---:|---:|
| 逐条新闻抽取 | 17 | 34,522 | 25,984 | 8,538 | 15,221 |
| `report-v3` 报告分析 | 3 | 48,281 | 27,520 | 20,761 | 8,331 |
| 合计 | 20 | 82,803 | 53,504 | 29,299 | 23,552 |

抽取阶段包含 16 条新闻的基础请求和 1 次结构化输出自动修复。报告阶段包含：

1. 第一次返回的工具参数不是合法 JSON；
2. 第二次返回缺少必需的 `top_events`；
3. 第三次通过 Schema、事实引用、中文和事件引用检查。

完整修复上下文保存在 `data/runs/2026-08-12/model_messages/report.messages.json`。

## 费用估算

计算公式：

```text
费用 = 缓存命中输入 × ¥0.5 / 1,000,000
     + 缓存未命中输入 × ¥2 / 1,000,000
     + 输出 × ¥8 / 1,000,000
```

| 阶段 | 缓存命中费用 | 缓存未命中费用 | 输出费用 | 估算合计 |
|---|---:|---:|---:|---:|
| 逐条新闻抽取 | ¥0.0130 | ¥0.0171 | ¥0.1218 | **¥0.1518** |
| `report-v3` 报告分析 | ¥0.0138 | ¥0.0415 | ¥0.0666 | **¥0.1219** |
| 完整业务产物 | ¥0.0268 | ¥0.0586 | ¥0.1884 | **¥0.2738** |

按 16 条新闻计算，抽取阶段平均约 ¥0.0095/条；包含最终报告后，平均约 ¥0.0171/条。费用主要来自结构化中文输出，而不是缓存命中的重复 Prompt。

## 延迟

`report-v3` 运行已加入正式阶段计时：

| 阶段 | 耗时 |
|---|---:|
| 复用抽取状态与初始化 Agent | 0.917 秒 |
| 事件聚合 | 0.007 秒 |
| DeepSeek 报告分析（含两次修复） | 60.154 秒 |
| 报告和图表渲染 | 0.042 秒 |
| 最终质量验证 | 0.005 秒 |
| 本次安全续跑总耗时 | **61.136 秒** |

首次抽取运行发生在加入阶段计时之前。根据抽取开始时间与最后一条洞察检查点文件时间，16 条新闻的顺序抽取约为 105 秒；这是文件时间推算值，不作为精确基准。后续新运行会在 Manifest 中直接记录阶段耗时。

## 逐条与小批量的成本权衡

当前抽取使用 `batch_size=1`。如果改为每批 4 条，在全部一次成功的理想情况下，基础请求可从 16 次降至 4 次，但原始新闻内容、结构化输出内容和证据字段并不会消失，主要减少的是重复的 instructions 与输出 Schema 前缀。

现有 17 次抽取请求共产生 25,984 个缓存命中 Token，平均每次约 1,528 个。即使把基础请求从 17 次理想化压缩到 4 次，最多减少约 19,900 个缓存命中 Token；按当前价格计算，节省不到 ¥0.01，约占抽取费用的 6.5%。这只是上界估算，实际结果取决于缓存命中、批量输出长度和重试次数。

小批量更可能改善的是网络往返次数，而不是输出 Token 成本。但一条记录格式错误可能使整个数组校验失败，还需要额外实现“部分成功保存、单条重试和事实归属检查”。因此，我在当前版本保留逐条抽取，以换取证据逐字校验、精确重试、失败隔离和一条新闻对应一份消息记录。如果后续单次数据量明显增长，我会先对 3～5 条的小批量方案做准确率、部分失败恢复和总延迟基准测试，再决定是否切换，而不会只根据请求数优化。

## 可观测性实现

当前 `run.json` 新增：

- `performance.duration_seconds`：本次流水线总耗时；
- `performance.stage_duration_seconds`：准备、抽取、聚合、报告、渲染和验证耗时；
- `performance.extraction_mode`：区分真实模型调用与安全复用；
- `usage`：抽取、报告和总 Token/请求量；
- `schema_versions`：区分事实层 Schema 1.0 与报告 Schema 1.1。

单独运行抽取命令时，抽取 Manifest 也会记录 `duration_seconds`。
