# Harness Engineering 设计

## 选型

我选择开源 Pydantic AI 作为 Agent 核心，并在仓库内实现轻量 Harness。选择依据是它原生支持 Pydantic 结构化输出、有限重试、生命周期 Hooks、消息历史和可注入测试模型，正好覆盖这条流水线最需要的输出约束、错误恢复和可观测性。

当前流程是两个边界清晰的顺序阶段，没有复杂分支或长期状态，因此我没有引入更重的图编排框架。需要付出的代价是检查点、版本匹配、证据验证和 Manifest 由项目自行维护，但这些机制也因此保持透明、便于审查。

## 两个有边界的模型阶段

### 1. 逐条洞察抽取

`extract-v2` 每次只接收一条新闻。`extract-news-insight` Skill 与 Hooks 共同约束：

- evidence 必须是来源内容的连续子串；
- 摘要、影响理由、情绪理由和风险/机会必须使用中文；
- 模型不能生成来源 ID、模型名、时间或 Prompt 版本；
- 结构或证据失败最多修复 2 次，仍失败则隔离。

### 2. 事件层报告分析

`report-v3` 只读取已验证的事件摘要、带 ID 的事实、四维影响、重要度和 ID，不读取完整原始文章。报告 Hooks 要求：

- Top 事件 ID 和顺序必须与确定性排名完全一致；
- 趋势必须恰好覆盖技术、应用、政策、资本；
- 趋势只能引用已知事件；
- 执行摘要、Top 背景、影响判断和趋势只能引用已提供的事实 ID；
- 每个趋势引用的事件都必须至少有一个事实 ID 支撑；
- 所有正文必须是中文；
- 内部 `event_###` ID 不能出现在读者正文。

模型输出只负责叙事，程序再将事件 ID 映射为真实新闻来源 ID，并保留 `fact_id → 新闻 ID → evidence` 的审计链。

## 可续跑与版本安全

每条抽取结束后都会原子写入洞察、消息、Trace 和隔离记录。续跑前必须同时匹配：

1. 源输入 SHA-256；
2. 模型名；
3. 抽取 Prompt 版本；
4. Schema 版本。

任一项变化都会清理该日期的旧运行状态并重新抽取；全部匹配且 16 条已成功时，抽取阶段直接复用，报告分析仍可独立重新生成。

## 逐次尝试审计

`data/runs/<日期>/manifests/extract.attempt-###.json` 永久保留每次批量尝试的尝试数、续用数、有效数、隔离数、失败 ID 和当次 Token。最终 `extract.json` 表示最新状态，`run.json` 汇总完整尝试历史。

即使 Provider 或最终验证抛出异常，Hook Trace 也通过 `ExtractionRunError` 带回批处理层保存，不再丢失失败轨迹。
