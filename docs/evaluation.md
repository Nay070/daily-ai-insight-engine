抽取阶段一次批量尝试完成 16 条，其中结构化输出自动修复产生 1 个额外请求。`report-v3` 首次输出不是合法 JSON，第二次缺少必需的 `top_events`，第三次通过 Schema、事实 ID、中文和事件引用检查。最终没有隔离项。

这两次失败验证了两个设计判断：结构化输出不能只依赖 Prompt 自觉，报告阶段也需要独立 Schema 与引用检查；同时，完整修复上下文必须保留，否则最终报告看似正常，却无法解释模型曾经在哪里偏离合同。代价是报告阶段本次用了 3 次请求，延迟主要也集中在修复过程。

完整 Token、缓存用量、Prompt 版本、输入哈希、阶段耗时和尝试历史见 `data/runs/2026-08-12/manifests/run.json`。费用计算与逐条/小批量分析见 `docs/cost-and-performance.md`。

## 自动化覆盖

- Schema、时间、数据覆盖和去重；
- evidence 逐字校验和中文叙述校验；
- Skill 注入与生命周期 Trace；
- 仅重跑缺失项；
- Prompt 版本不匹配时禁止续用；
- 合并成员隔离时安全降级；
- 报告事实 ID 必须存在，并属于对应事件和来源；
- 完整 `run-live` 编排、报告分析、图表和最终验收；
- 端到端测试不联网，也不生成第二套业务数据。

自动质量门可以证明结构、证据片段、引用、覆盖和流程可复现，但不能完全替代人工事实准确率评审。下一步我会优先增加人工抽样准确率和事件聚类精确率/召回率；这比先扩充界面或存储层更能降低当前系统的核心风险。
